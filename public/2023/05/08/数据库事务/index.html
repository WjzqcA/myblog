数据库事务

数据库事务是数据库管理系统（DBMS）执行的基本工作单元，它将一组数据库操作组合成一个逻辑上的整体。这些操作要么全部成功执行，要么全部不执行，确保数据库从一个一致性状态转变到另一个一致性状态。

核心作用：保证数据的完整性和一致性，防止因系统故障或操作错误导致数据处于中间状态。

一、事务的四大特性（ACID）

ACID 特性是事务最核心的概念。

特性 全称 含义
原子性（Atomicity） 事务是最小执行单元，不可再分 转账操作中，扣款和入账必须同时成功或同时失败，不能只完成其中一步
一致性（Consistency） 事务执行前后，数据满足完整性约束 银行账户转账后，转出金额与转入金额之和必须等于原总额
隔离性（Isolation） 多个事务并发执行时相互隔离，互不干扰 多个用户同时操作账户时，彼此的操作不会互相影响数据状态
持久性（Durability） 事务提交后，数据修改永久保存 转账成功后，即使系统崩溃，数据也不会丢失

执行 SQL 但未提交是怎么运作的？

当执行一个修改类的 SQL（例如 UPDATE），即使未提交，数据库内部会进行以下操作：

1. 缓冲池中的数据页（Data Page）

  • 数据库将磁盘上的数据页加载到内存的缓冲池中。
  • 修改直接作用于缓冲池中的数据页，并加锁，修改对其他事务不可见。

2. 生成 Undo 日志（回滚日志）

  • 数据库为修改生成 Undo 日志，用于回滚事务。
  • 如果事务回滚，数据库使用 Undo 日志恢复数据原状。

3. 标记为“未提交”状态

  • 修改的数据被标记为某个事务 ID 的“未提交”状态，其他事务（在高隔离级别下）会跳过这些数据。

三、并发事务问题

1. 脏读

事务 A 读取了事务 B 已修改但未提交的数据，若 B 回滚，A 读取的数据即为“脏数据”。

2. 不可重复读

事务 A 在同一事务中多次读取同一数据时，由于事务 B 中途修改并提交，导致 A 前后读取结果不一致。

3. 幻读

事务 A 按条件查询数据时，事务 B 插入或删除符合条件的记录并提交，导致 A 再次查询（当前读）时结果集行数发生“幻觉”般的变化。

四、事务隔离级别

事务隔离级别用于解决并发事务问题。以下是四种隔离级别：

  1. 读未提交（Read Uncommitted）：允许读取尚未提交的数据，可能导致脏读。
  2. 读已提交（Read Committed）：只能读取已提交的数据，解决脏读问题。
  3. 可重复读（Repeatable Read）：解决不可重复读，事务内始终读取事务开始第一次快照读时的版本，即使其他事务提交修改，当前事务仍读取历史版本。本事务内修改会更新。如果不存在当前读，可重复读下快照读可以避免幻读。如果本事务当前读且和其他事务当前读数据有交集(比如A事务增加了一个数据，user=‘zz’)，A没有提交的情况下B不能对新增加的user=‘zz’进行修改，因为有锁会阻塞。如果A提交之后，B再对user=‘zz’进行修改，那么以后当前读也可以看到这个数据 。。
  4. 串行化（Serializable）：通过锁机制强制事务串行执行，解决幻读。

mysql默认可重复读

五、MVCC (多版本并发控制)

事务隔离级别是概念上的，MVCC 是具体的实现（在 MySQL 的 InnoDB 引擎下，RC 和 RR 基于 MVCC 进行并发事务控制）。

MVCC 是一种并发控制机制，它通过为每个事务提供“数据快照”来避免加锁读取，从而提高并发性能。

  • 简单说就是：不同事务看到的同一条记录，可能是不同的版本。
  • MVCC 是为了解决：读写冲突（读阻塞写、写阻塞读）。

MVCC 实现的核心在于：为同一条记录维护多个版本（版本链），不同事务根据其启动时间读取“对它可见”的版本。

1. 当前读和快照读

当前读 = 读取数据库中最新版本的数据，并且加锁，阻塞其他事务的修改操作（当前读）

  • 通常会加共享锁（S）或排他锁（X），保证读取的是“当前最新且一致的数据”。
  • 所有的当前读操作都会加锁，等到 commit 或 rollback 后才会释放，期间其他事务不能修改数据库。
  • 常见的 SQL 操作包括：（修改或者加锁的 select）
    • SELECT … FOR UPDATE
    • SELECT … LOCK IN SHARE MODE
    • UPDATE
    • DELETE

当前读不使用快照视图，它读取的是最新提交或未提交的数据（取决于隔离级别）。

快照读读取的是数据在某一时刻的一致性快照（非当前最新值）

  • 是只读操作，不适用于修改。不会阻塞其他事务。
  • 每个事务会有自己的 Read View（读取视图），从中判断哪些版本对它“可见”。
  • 常见 SQL 操作：普通的 SELECT（非 for update）
  • 使用 MVCC 提供一致性视图，不直接读最新数据，而是读“我事务可见的版本”。

2. MVCC 的三个组件

Undo Log隐藏字段

每一行记录都会包含几个用户不可见的字段：

DB_TRX_ID：创建或者最后一次修改该记录的事务 ID。

DB_ROW_ID：隐藏主键。

DB_ROLL_ID：回滚指针（和 UNDO LOG 一起使用），指向上一次版本变化的数据信息。

Undo Log：回滚日志

当不同事务对同一条记录做修改的时候，会导致该记录的 undo log 形成一个线性表，也就是链表，链表的链首是最新的历史记录，而链尾是最早的历史记录。

Read View：事务在进行快照读时产生的视图

Read View 是一个数据结构，用于记录某个事务开始时数据库中活跃事务的状态。它本质上是一个“快照”，帮助事务决定在 MVCC 下读取哪个版本的数据。

Read View 是 MVCC 中用来判断某个数据版本（undo log 中的历史版本）是否对当前事务可见的依据。

  • 每行数据在 MVCC 中都有版本信息，包括创建该版本的事务 ID（trx_id）和删除该版本的事务 ID（如果有）。

  • 事务读取某行数据时，会根据 Read View 判断该行的版本是否可见：

    • 如果 trx_id < m_up_limit_id，说明该版本在 Read View 创建前已提交，可见。
    • 如果 trx_id >= m_low_limit_id，说明该版本在 Read View 创建后生成，不可见。
    • 如果 m_up_limit_id <= trx_id < m_low_limit_id，检查 trx_id 是否在 m_ids 中：
      • 如果在 m_ids 中，说明该版本由活跃事务创建，不可见。
      • 如果不在 m_ids 中，说明该版本已提交，可见。
    • 如果 trx_id 等于 m_creator_trx_id，说明是当前事务自己的修改，可见。

  • 读已提交（Read Committed）：每次快照读生成新的 Read View，可能看到其他事务提交的新数据。

  • 可重复读（Repeatable Read）：事务在第一次快照读时生成 Read View，整个事务期间使用同一视图（InnoDB默认本事务修改的自己永远可见），确保多次读取结果一致。（以下具体解释以下可重复读隔离下能否出现幻读）

    • 事务A只进行快照读会出现幻读吗：不会看见，因为事务A只会看到第一次快照读生成的Read View，其他事务怎么改都不会变。

    • 事务A进行快照读，如果事务B新增或删除后提交，事务A当前读会产生幻读

    • 事务A进行快照读，如果事务 B新增后提交，事务 A 也进行当前读并且与事务 B 的修改（新增或删除）数据出现交集，则以后的事务A快照读会看到这部分交集从而产生幻读。（特殊情况）

  • 串行化

    串行化通过范围锁或冲突检测彻底防止幻读，确保事务间完全隔离。

    实现方式：对所有读取的记录和扫描的范围加共享锁（S 锁），对写操作加排他锁（X 锁）。

    • 范围锁（Range Lock 包括边界）与间隙锁（Gap Lock 不包括边界）：
      • 串行化级别下，任何范围查询（如 SELECT … WHERE value > 10）都会对查询涉及的数据范围加锁，包括现有记录和可能的间隙（Gap）。
      • 阻止其他事务在查询范围内插入或删除记录。
      • 例如，事务 A 查询 WHERE value > 10，InnoDB 会锁定所有 value > 10 的记录及相关间隙，事务 B 无法插入或删除符合条件的记录，直到事务 A 提交。
    • 读写加锁：
      • 在串行化级别下，所有读操作（包括快照读）都被视为加锁读（类似 SELECT … FOR SHARE 或 SELECT … FOR UPDATE）。
      • 读操作会对访问的记录加共享锁（S 锁允许多个事务同时读，但阻止写），写操作加排他锁（X 锁独占资源，阻止任何其他操作）。
      • 这确保事务 A 的读操作范围不会被其他事务的写操作（插入、删除、更新）干扰。
