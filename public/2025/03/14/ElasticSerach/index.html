ElasticSerach

Elastic Search

一、核心特点

  1. 分布式架构
    • 数据自动分片（Shard）存储，可水平扩展，ES 将索引拆分成多个分片。
    • 分片副本（Replica）机制，保证高可用和负载均衡。

  1. 近实时搜索
    • 数据写入后秒级可被搜索（延迟通常在 1 秒内），兼顾实时性与性能。
  2. 全文检索能力
    • 基于 Lucene 的倒排索引，支持分词、同义词、模糊匹配等高级文本处理。
    • 内置多种分词器（如中文 ik 分词器），适配多语言场景。
  3. 强大的聚合分析
    • 支持复杂的统计分析（如分组、求和、平均值），可用于数据可视化（配合 Kibana）。
  4. RESTful API
    • 所有操作通过 HTTP 接口完成，支持 JSON 格式，易于集成到各种语言（Java、Python 等）。

二、核心概念

Elasticsearch 概念 对应关系型数据库 说明
Index（索引） 数据库（一个表） 存储一类数据的集合
Document（文档） 行（Row） 一条 JSON 数据，基本信息单元
Field（字段） 列（Column） 文档中的一个属性
Mapping（映射） 表结构（Schema） 定义字段类型、分析器等
Shard（分片） 数据分区 数据水平拆分，提高性能和容错
Replica（副本） 备份 分片的副本，提供高可用

三、分词原理

3.1分词方法

ES分词的原理就是把一段文本拆分成一个个 Token（词项），并为每个词建立倒排索引，以便快速匹配搜索。

三大组件详解：

组件 作用 示例
Character Filter 预处理原始文本（清理 HTML、替换字符）

Hello

→ Hello
Tokenizer 按规则切分成 Token “I love China!” → [“I”, “love”, “China”]
Token Filter 过滤、转换 Token（小写、去停用词、词干提取） [“Running”, “jumps”] → [“run”, “jump”]

Tokenizer默认只有英文分词器，需要手动下载中文分词器如IK Analyzer，它有两种模式

模式 说明 示例
ik_smart 智能分词（最少切分），查找时使用，提供更合理的查找词 “中华人民共和国” → [“中华人民共和国”]
ik_max_word 细粒度分词（最多切分），适用于底层索引分词，提供更细粒度的索引 → [“中华”, “华人”, “人民”, “共和”, “国”, …]

3.2倒排索引

将输入的文本进行分词后，对分词进行存储以便接下来的查找，这里使用了倒排索引。所谓的倒排索引就是说将分词后的结果作为索引建立起词到文档的映射（正排索引是文档到词）。

整个流程为将数据库中的数据存储到es中根据特定的分词器进行分词，然后使用倒排索引进行存储和映射。当进行搜索的时候，同样对文本进行分词然后根据索引映射到所有包含这个词的目标。

倒排索引结构图：

es打分规则：会设定相关性

（1）词频（TF, Term Frequency）：查询词在文档中出现的次数，出现次数越多，得分越高。

（2）反向文档频率（IDF, Inverse Document Frequency）：查询词在所有文档中出现的频率。词在越少的文档中出现，IDF 值越高，得分越高。

（3）文档长度：较短的文档往往被认为更相关，因为查询词在短文档中占的比例更大。

4.2基本语法

1）DSL 查询（推荐核心方式）

DSL 是 Elasticsearch 原生的查询语言，基于 JSON 格式，功能强大、灵活，能充分利用 ES 的各种搜索特性（如分词、权重、聚合等）。

特点：

  • 完全贴合 ES 的底层能力，支持所有高级查询（如全文检索、布尔组合、模糊匹配、聚合分析等）。
  • 结构清晰，通过嵌套 JSON 表达复杂查询逻辑。

基本格式：

通过 GET /索引名/_search 接口，请求体中传入 DSL 语句：

适用场景：

  • 复杂的全文搜索、条件组合查询。
  • 需要使用 ES 特有功能（如分词、权重调整、聚合分析）。
  • 生产环境中推荐使用，性能和可控性更强。

2）SQL 查询（兼容传统 SQL 习惯）

ES 支持通过 SQL 语句查询数据，降低了熟悉 SQL 的开发者的使用门槛，底层会自动将 SQL 转换为 DSL 执行。

特点：

  • 语法与标准 SQL 类似，易于上手（如 SELECT、WHERE、GROUP BY 等）。
  • 功能有限，部分高级特性（如复杂聚合、分词调优）仍需依赖 DSL。

基本格式：

适用场景：

  • 快速查询、临时数据分析，适合熟悉 SQL 的开发者。
  • 简单的条件查询、排序、分页场景。
  • 不适合复杂的全文搜索或需要深度定制的查询。

总结：

  • DSL：ES 原生查询语言，功能全面、灵活，适合复杂场景和生产环境，是核心推荐方式。
  • SQL：兼容传统 SQL 语法，上手简单，适合简单查询和快速分析，但功能有限。

五、数据库同步方法

一般情况下，如果做查询搜索功能，使用 ES 来模糊搜索，但是数据是存放在数据库 MySQL 里的，所以说我们需要把 MySQL 中的数据和 ES 进行同步，保证数据一致（以 MySQL 为主）。

数据流向：MySQL => ES（单向）

数据同步一般有 2 个过程：全量同步（首次）+ 增量同步（新数据）

1) 定时任务

比如 1 分钟 1 次，找到 MySQL 中过去几分钟内（至少是定时周期的 2 倍）发生改变的数据，然后更新到 ES。

优点：

  • 简单易懂、开发、部署、维护相对容易。
  • 占用资源少，不需要引入复杂的第三方中间件。
  • 不用处理复杂的并发和实时性问题。

缺点：

  • 有时间差：无法做到实时同步，数据存在滞后。
  • 数据频繁变化时，无法确保数据完全同步，容易出现错过更新的情况。
  • 对大数据量时更新处理不够高效，可能会引入重复更新逻辑。

应用场景：

  • 数据实时性要求不高：适合数据短时间内不同步不会带来重大影响的场景。
  • 数据基本不发生修改：适合数据几乎不修改、修改不频繁的场景。
  • 数据容忍丢失

2) 双写

写数据的时候，必须也去写 ES；更新删除数据库同理。

可以通过事务保证数据一致性，使用事务时，要先保证 MySQL 写成功，因为如果 ES 写入失败了，不会触发回滚，但是可以通过定时任务 + 日志 + 告警进行检测和修复（补偿）。

优点：

  • 方案简单易懂，业务逻辑直接控制数据同步。
  • 可以利用事务部分保证 MySQL 和 ES 的数据一致性。
  • 同步的时延较短，理论上可以接近实时更新 ES。

缺点：

  • 影响性能：每次写 MySQL 时，需要同时操作 ES，增加了业务写入延迟、影响性能。
  • 一致性问题：如果 ES 写入失败，MySQL 事务提交成功后，ES 可能会丢失数据，或者 ES 写入成功，MySQL 事务提交失败，ES 无法回滚，因此必须额外设计监控、补偿机制来检测同步失败的情况（如通过定时任务、日志和告警修复）。
  • 代码复杂度增加，需要对每个写操作都进行双写处理。

应用场景：

  • 实时性要求较高
  • 业务写入频率较低：适合写操作不频繁的场景，这样对性能的影响较小。
