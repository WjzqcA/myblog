Docker

一、Docker架构

Docker 是一个开源的容器化平台，用于构建、部署和运行应用程序。它通过容器技术实现轻量级虚拟化，允许开发者将应用程序及其依赖打包到一个可移植的容器中，从而保证在不同环境中运行的一致性

通俗的讲就是Docker 允许用户直接下载别人已经打包好的应用镜像（软件以及环境配置），运行在本地的容器里，无需自己再单独下载安装和配置复杂的环境，就像把一个“软件盒子”拿来用。

1.1 什么是镜像和容器？

镜像：Docker 镜像是一个只读的模板，包含了运行一个应用程序所需的操作系统环境 + 程序代码 + 配置 + 依赖库。

特点：

  • 只读：镜像一旦创建，内容不可修改。如果需要更改，必须基于现有镜像构建一个新镜像。
  • 分层结构：镜像由多层组成，每一层表示一个指令（如安装软件、复制文件）。这些层可以被缓存和复用，节省存储空间和构建时间。
  • 可共享：镜像可以上传到 Docker Registry（如 Docker Hub），供他人下载使用。

容器：容器是镜像的运行实例，是一个独立的、轻量级的运行环境，包含了从镜像复制过来的内容，并在其上运行应用程序。

特点：

  • 可运行：容器是镜像的动态实例，运行后可以执行应用程序或服务。
  • 隔离性：每个容器有自己的文件系统、网络、进程空间，互不干扰（通过 Linux 的 Namespaces 和 Cgroups 实现）。
  • 轻量：容器只包含应用和必要的依赖，不包括整个操作系统内核，因此启动快、占用资源少。
  • 可销毁：容器停止后可以轻松删除，默认情况下不会保留数据（除非使用数据卷或绑定挂载）。

可以把容器视为镜像的运行状态

1.2 思考：

  1. 镜像是否占有大量空间？

    多个镜像可以共享相同的底层层，新建镜像只增加变动的部分，不会复制整个镜像内容（比如都用到Ubuntu，那么有一个镜像中包含就够了）。支持使用体积非常小的基础操作系统镜像。

  2. 一个容器只能运行一个镜像吗？

    一个容器只能基于一个镜像运行，多个容器可以使用同一个镜像。

    让我们对比一下三种部署方式。传统方式在一个os上直接部署多个应用（Web、mysql、redis等），这样版本可能会有冲突。虚拟机部署的话，每一个虚拟机启动都要大量时间，启动慢，占用资源大，维护多个操作系统麻烦。

    对于Docker的部署方式，每个服务打包成一个 Docker 镜像，自带系统环境（每一个应用都配置好了环境），容器隔离，秒级启动，扩展简单。

  3. 不同容器之间会出现环境冲突吗？

    不会，这是 Docker 最核心的优势之一：容器之间完全隔离

    每个容器都有自己的文件系统

    • 每个容器基于镜像创建一个独立的文件系统（包含环境变量、配置、依赖等）。
    • 容器之间看不到彼此的文件、库、配置，也不会互相修改或干扰。

    ✅ 举例：

    • 容器 A 用的是 Python 3.10
    • 容器 B 用的是 Python 3.11
    • 两者不会冲突，因为它们各自运行在独立的文件系统里。

    每个容器都有自己的进程空间

    • 容器内运行的进程只能看到自己的进程，无法访问其他容器的进程。

    ✅ 举例：

    • 容器 A 运行的是 MySQL 进程
    • 容器 B 运行的是 Redis
    • 它们互相“看不见”，更不会相互干扰。

    每个容器都有自己的网络空间

    • 每个容器默认拥有自己独立的 IP 和端口空间。
    • 容器之间通信需要显式配置（比如用 docker network 或 docker-compose 连接它们）。

    ✅ 举例：

    • 容器 A 的 Flask 监听 5000 端口
    • 容器 B 的 Node.js 也监听 5000 端口
    • 没问题！因为它们的端口分别在各自独立的网络空间中，不冲突。

1.3 Docker工作流程

如图，概括一下Docker的工作流程：

  1. 用户通过 Docker 客户端发送命令（如 docker run）。
  2. Docker Daemon（后台运行的服务程序，负责接收 Docker 客户端的命令，并完成镜像构建、容器管理、网络配置等所有核心操作） 接收命令，检查本地是否有需要的镜像。
  3. 如果没有镜像，Daemon 从注册中心（如 Docker Hub）拉取镜像。
  4. Daemon 根据镜像创建容器，分配网络和存储资源。
  5. 容器启动并运行，应用在隔离环境中执行。
  6. 用户可以通过客户端管理容器（停止、删除、查看日志等）。

2.2 容器相关

这里说一下端口映射，本质是打通主机与容器之间的网络连接（主机访问容器）

为什么需要端口映射？

Docker 容器默认运行在独立的网络环境中，拥有自己的虚拟 IP 地址（如 172.17.0.x），与主机的网络是隔离的。例如容器内运行了一个 Nginx 服务，默认监听 80 端口。但此时直接通过主机的 IP 地址访问 80 端口，是无法连接到容器内的 Nginx 的 —— 因为容器的网络和主机网络是 “分开的”。当配置端口映射后，docker能直接将外部主机的请求（主机ip：主机端口）转发到对应地容器上（容器ip：容器端口）。

端口可以重复吗？

外部主机的端口不能重复，容器是独立的因此可以重复。配置是要防止端口冲突，不要让一个主机端口对应多个容器

三、存储

3.1 目录挂载

是一种将宿主机的目录或文件与容器内的目录或文件建立关联的技术。通过挂载，容器可以直接读写宿主机的文件，同时宿主机也能访问容器生成的数据，解决了容器与宿主机之间的数据共享和持久化问题（容器删除后，挂载的数据不会丢失）。即外部或者内部修改文件，另一个都会同步更新。

使用目录挂载要在启动镜像的容器的时候加上-v

3.2 卷映射

因为目录挂载，外部初始化的文件是空文件，相应的容器内的文件也变成了空文件。如果我们想要对配置文件进行挂载，那么容器无法启动，因为配置文件是空的。

卷映射就是保存容器内部文件内容的目录挂载

卷是 Docker 官方推荐的持久化方案，它是一个由 Docker 引擎创建和管理的独立于容器的存储目录。当你创建卷并挂载到容器时，Docker 会在宿主机的特定目录下自动生成一个文件夹，用于存储该卷的数据

四、网络

容器之间的相互访问：先说一种访问方式，在容器B内部 curl 主机ip：端口号。这个的整体流程是容器B先去访问主机，再去访问容器A，这样有点麻烦。

如何能够更加合理的让容器之间通信呢？

docker有一个机制，每一个容器启动时都会加入一个默认的网络docker0（使用ip a可以看到地址）。在容器内部可以直接用容器的ip进行相互访问，使用docker inspect 容器名就可以查看对应容器的细节。这样在容器B中可以 curl 容器A的ip：容器A的端口进行访问

但是这样也有一个问题，ip可能是变化的而且记忆不方便，我们可以自定义网络，使用域名进行访问（docker规定docker0不支持域名访问）
