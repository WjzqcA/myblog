JVM

一、JVM简介

1.1JVM概念

JVM本质上是一个运行在计算机的一个程序，他的职责是运行JAVA字节码文件。

java虚拟机负责将字节码指令解释为机器码，这样在不同的平台可以用不同的JVM将字节码解释为适合当前平台（windows、linux等）的机器码。

JVM的主要功能：

  1. 解释和运行。对字节码文件中的指令，实时的解释成机器码，让计算机执行。
  2. 内存管理。自动为对象、方法等分配内存。自动的垃圾回收机制，回收不在使用的对象。
  3. 即时编译。对热点代码进行优化，提升执行效率。（也就是会把多次需要调用的代码的机器码放到内存中，以后直接调用即可）

1.2字节码文件详解

1.2.1JVM的组成

  1. ClassLoader负责将字节码文件加载到JVM内存
  2. 本地方法接口，是连接 Java 代码与本地代码（如 C/C++、汇编等）的桥梁。让 Java 程序能调用本地代码、本地代码也能回调 Java 代码。（本地代码指的是直接针对特定硬件架构（如 x86、ARM）和操作系统（如 Windows、Linux）编译的机器码，它无需虚拟机 / 解释器中转，可直接被 CPU 执行。）

1.2.2字节码文件的组成（.class文件二进制存储）

Jclasslib或者插件可以展示字节码文件的内容，字节码文件中包含了基础信息、常量池、字段、方法还有属性等信息。

  • 魔数：魔数是一串固定的、具有标识作用的数值 / 字符序列，核心作用是让程序 / 系统快速识别数据的类型、格式或合法性，相当于给数据 / 文件 / 协议包贴的 “身份标签”。（文件无法通过扩展名确定文件的格式，扩展名只是让格式对应的软件打开文件）
  • 主版本号：指的是编译字节码文件的JDK版本号，主版本号用来标识大版本号，用主版本号减去44就是jdk的版本。比如52就是JDK8
  • 常量池：就是一张表，虚拟机根据这张常量表找到要执行的类名、方法名、参数类型、字面量（字面量包括：1.文本字符串 2.八种基本类型的值 3.被声明为final的常量等）等信息。字段值相同会直接指向常量池中的同一个字面量。（日常说的常量池一般指的是运行时常量池，也就是静态常量池加载到内存后的状态）
  • 方法：源文件中的类、方法和接口等信息存放到字节码文件中。

二、类加载

2.1类的生命周期

类的生命周期描述了一个类从加载到使用再到卸载的整个过程

2.1.1加载阶段

  1. 加载字节码信息。加载阶段的第一步是类加载器根据类的全限定名通过不同的渠道以二进制流的方式获取字节码信息。程序员可以使用Java代码拓展的不同的渠道。
  2. 将信息保存到内存的方法区，并创建InstanceKlass（c++实现）存储类的所有底层信息（字段、方法、常量池等类元数据）
  3. 在堆内存中创建 java.lang.Class 对象作为方法区元数据的访问入口，让该对象的内部指针指向方法区的 InstanceKlass（这样做是因为InstanceKlass是C++实现的不能直接用java访问同时避免恶意代码直接修改InstanceKlass）

  • Java 程序中通过 Object.getClass()、Class.forName() 获取的是堆中的 Class 对象；

  • 所有对类元数据的操作（反射、调用方法），最终都会通过 Class 对象关联到 InstanceKlass 完成。

问题：为什么不能直接用户访问方法区的对象，而是要在创建一个 java.lang.Class 对象

  1. InstanceKlass是C++实现的，用户不能直接通过java来访问，所以由jvm实现
  2. 如果InstanceKlass被直接访问，那么所有数据都会暴露，所以java.lang.Class 只会提供部分数据的访问避免风险

2.1.2连接阶段

连接由验证、准备和解析三个阶段组成

验证阶段：主要是检测Java字节码文件是否遵循了Java虚拟机规范中的约束，这个阶段不需要程序员参与。

准备阶段：为类的静态变量（类变量，static 变量）分配内存，并设置默认初始值（而非程序员定义的 “显式初始值”，为变量赋真实值在初始化阶段）。如果是final修饰的会直接赋真实值

解析阶段：将方法区中类元数据的符号引用替换为直接引用

类型 定义 示例（以调用java.lang.String.length()为例）
符号引用 用字符串描述的、与内存地址无关的引用，仅包含 “目标的全限定名 / 名称 / 描述符” java/lang/String.length:()I（类全限定名 + 方法名 + 方法描述符）
直接引用 指向目标在内存中实际位置的引用（如指针、偏移量、句柄），与内存布局强绑定 指向String.length()方法在方法区的内存地址的指针

实际实现使用延迟解析策略，不提前解析所有需要的符号、数据或依赖，而是等到首次真正使用时才执行解析操作，以此减少初始化开销、提升启动速度。

2.1.3初始化阶段

初始化阶段是类加载过程中首次执行 Java 代码的阶段，它的核心是执行字节码文件中clinit部分的字节码指令（由 JVM 自动生成，程序员无法直接调用），整个流程严格遵循 “父类优先、顺序执行” 的原则。 用来进行类初始化，也就是static修饰的。对象初始化通过也就是构造方法实现。

实现static 变量（类变量）、static 方法（类方法）、static 代码块和static 内部类（这些统称为静态成员）的初始化。如果没有static修饰，以下方式也会初始化：

主动引用场景 示例
首次创建类的实例（new 关键字），这是对象初始化 new User();
调用类的静态方法 Math.max(1,2);
访问类的静态变量（非 final 编译期常量） User.count = 10;
反射调用类的方法 / 字段 Class.forName(“com.User”);
初始化子类时（父类未初始化） 初始化Son类，先初始化Father类
执行包含 main 方法的主类（main所在的类会初始化） 运行java Main，初始化 Main 类

几个需要注意的问题！！！

  1. 注意类的初始化和对象的初始化的区别：

只有静态成员才是类初始化，在准备阶段进行内存分配和设置默认值。对象初始化是要在new的情况下才会初始化，不属于类加载过程，他会由jvm在堆中分配内存并赋值。

  1. 如果一个类的变量被static和final修饰(也就是常量)，另一个类调用这个变量，这个类会被初始化吗？

不会，static final为常量，其值在编译阶段就能确定（字面量、常量表达式），编译器会把这些常量直接 内联到调用类的字节码常量池中，也就不需要通过初始化类获得值了。

  1. 父类和子类之间的初始化

直接访问父类的静态变量，不会触发子类的初始化。子类初始化之前要想给父类初始化。

这里的输出的是c=1，因为c是在父类中定义的，因此访问子类的c不会初始化b直接去初始化父类

  1. 局部变量不会初始化，因为它存在栈中，它没有被jvm分配默认值，因此一定要自己赋值。

2.2类加载器

JVM 中的类加载器（ClassLoader） 是 JVM 核心组件之一，核心作用是将编译后的字节码文件（.class 文件）加载到 JVM 内存中，并转换为 JVM 可识别的 Class 对象，同时完成类的链接、初始化等后续流程，是类能够被 JVM 执行的前提。

2.2.1类加载器的分类

一种是由java编写的，一种是有jvm底层源码实现的（c++/c），所有的java实现的类加载器都继承自ClassLoader类。

jdk8之前和jdk9之后有比较大的差异，先说一下jdk8。

  1. jdk1.8

启动类加载器：是有Hotspot虚拟机提供的、使用c++编写的类加载器。默认加载Java安装目录/jre/lib下的类文件（核心类库），比如rt.jartools.jar,resources.jar等。启动类加载器不能被java获得，因为它是使用c++编写的。

如何通过启动类去加载用户的jar包？

直接将jar包放到/jre/lib下是不行的，因为JVM 会校验核心库的签名，非官方签名的类即使放在该目录也会被忽略，仍由应用类加载器加载。

使用-Xbootclasspath/a:jar包目录/jar包名进行扩展更合理，将这个目录下的jar包同样加到启动类中，同样仅加载符合 JVM 核心类规则的类，而非任意类。

扩展类加载器和应用类加载器：

扩展类加载器和应用程序类加载器都是JDK中提供的、使用Java编写的类加载器。它们的源码都位于sun.misc.Launcher中，是一个静态内部类。继承自URLClassLoader。具备通过目录或者指定jar包将字节码文件加载到内存中。

扩展器加载器默认加载java安装目录/jre/lib/ext下的类文件（通用但不重要的类）。

  1. jdk1.9：引入了module的概念，类加载器在设计上发生了很多变化

**启动类加载器：**使用**Java编写**，位于jdk.internal.loader.ClassLoaders类中。Java中的BootClassLoader继承自BuiltinClassLoader实现从模块中找到要加载的字节码资源文件。启动类加载器依然无法通过代码获得，返回的仍然是null，保持了统一。

**平台类加载器：**原来的扩展类加载器被换成平台类加载器。平台类加载器遵循**模块化方式**加载字节码文件，所以继承关系从URLClassLoader变成了BuiltinClassLoader，BuiltinClassLoader实现了从模块中加载字节码文件。只能通过模块声明扩展

应用类加载器：改名为System ClassLoader

2.2.2双亲委派机制

由于Java虚拟机中有多个类加载器，通过全类名然后类加载器会去自己要找的路径中查找是否有该类，这就会产生问题。双亲委派机制的核心是保证核心类的唯一性（如java.lang.String仅由启动类加载器加载），防止用户自定义类篡改 JVM 核心 API，同时避免类的重复加载。

其核心思想是：当一个类加载器收到类加载请求时，它不会先自己加载，而是先把请求委派给父类加载器，如果自己没有加载过此类则逐层向上传递，直到顶层的启动类加载器；向下传递时，只有当父类加载器无法加载该类（在其搜索范围内找不到对应的类），子类加载器才会尝试自己加载。

以加载 com.example.MyClass 为例：

  1. 应用类加载器 收到加载请求，先委派给父类（扩展类加载器）；
  2. 扩展类加载器 收到请求，再委派给父类（启动类加载器）；
  3. 启动类加载器 检查自己的加载范围（rt.jar），找不到 MyClass，返回 “加载失败”；
  4. 扩展类加载器 收到父类失败的反馈，检查自己的范围（ext 目录），也找不到，返回 “加载失败”；
  5. 应用类加载器 收到反馈，最后在自己的 ClassPath 下查找，找到则加载，找不到则抛出 ClassNotFoundException。

解决的问题：

  1. 避免类重复加载：同一个类只会被最顶层的能加载它的类加载器加载一次，防止内存中出现多个相同的类对象；
  2. 保证核心类的安全：核心类（如 java.lang.String）只能由启动类加载器加载，避免用户自定义同名类替换核心类（比如自定义 java.lang.String 篡改逻辑），防止 “核心类被篡改” 的安全问题；
  3. 类加载的优先级：核心类库优先加载，保证 Java 基础环境的稳

2.2.3打破双亲委派机制（了解）

什么场景需要打破呢？

  1. 单Tomcat、JBoss 等容器（一个jvm）在运行多个web应用下，如果两个web应用有相同的类（如MyServlet），那么只会加载一个，这样会出现错误（现在一般都是一个tomcat只运行一个项目）。因此可通过自定义类加载器优先加载自身目录下的类
  2. 中间件需求：如 Dubbo、Spring，需自定义类加载逻辑（如加载外部插件、实现类隔离）。
  3. SPI 机制：如 JDBC（java.sql.Driver），核心接口在启动类加载器加载的 rt.jar 中，但实现类（如 MySQL 驱动）在应用类路径下，启动类加载器无法加载，需线程上下文类加载器反向委派。

三、运行时数据区域（JVM管理的内存）

3.1程序计数器

区别于计算机组成里的硬件程序计数器，这里只是软件层面的模拟。在代码执行过程中，程序计数器会记录下一行字节码指令的地址。执行完当前指令之后，虚拟机的执行引擎根据程序计数器执行下一行指令。每一个线程都有一个对应的程序计数器

程序寄存器在运行过程中会出现内存溢出吗？

程序寄存器只会存储一个固定长度的内存地址，不会出现溢出问题

3.2栈

3.2.1概要

栈是 JVM 运行时数据区的核心组成部分，和程序计数器一样线程私有，生命周期与线程完全绑定，核心作用是支撑 Java 方法的执行。

栈分为java虚拟机栈和本地方法栈，前者支撑 Java 方法（字节码方法） 的执行，后者支撑 native 方法的执行（比如 Object.getClass()、System.arraycopy() 等底层由 C/C++ 实现的方法，或自定义的 native 方法）

3.2.1java虚拟机栈

虚拟机栈是每个 Java 线程独有的内存区域，用于存储方法执行过程中的临时数据（比如局部变量、方法调用链路）以及维护方法调用的顺序。

核心结构：栈帧

虚拟机栈的基本存储单元是栈帧，只有调用方法时才会创建栈帧（main方法为栈顶），栈帧存放的是被调用方法所需的全流程信息，内部包含 4 个核心部分：

组成部分 核心作用
局部变量表 存储方法的局部变量（包括方法参数、方法内定义的变量、变量生效范围），按索引访问，以槽为一个基本单位，初始值为 null/0
操作数栈（栈帧里面也有栈） 在赋值的时候要先入一次栈，再弹出给局部变量表。最主要的功能是在方法执行过程中临时存放运算数据的 “临时栈”，比如执行 a+b 时，先压入 a、b，再弹出计算。Java 中绝大多数数据计算（如算术运算、逻辑运算）是在操作数栈中完成的。编译期就能确定最大深度
动态链接 指向当前方法所属类的运行时常量池，用于解析方法 / 字段的引用（比如调用 Object.toString() 时动态找到目标方法）
方法返回地址 记录方法执行完后，要回到调用方的哪个指令位置（比如 A 调用 B，B 执行完后回到 A 的下一条指令），然后交给程序计数器

每调用一个方法，JVM 就会在当前线程的虚拟机栈中压入一个新的栈帧；方法执行完成（正常返回 / 异常退出），栈帧就会被弹出。

在java运行抛出异常时，就将栈中遇到异常的栈帧一个个抛出，打印台输出的内容就是栈中栈帧的信息

问题：会不会出现内存溢出？

如果我们不指定栈的大小，jvm将创建一个具有默认大小的栈。大小取决于操作系统和计算机的体系结构。

  • Java虚拟机栈如果栈帧过多，占用内存超过栈内存可以分配的最大容量就会出现内存溢出。
  • Java虚拟机栈内存溢出时会出现StackOverflowError的错误

要修改Java虚拟机栈的大小，可以使用虚拟机参数-Xss。单位字节，必须是1024的倍数

3.2.3本地方法栈

  • Java虚拟机栈存储了Java方法调用时的栈帧，而本地方法栈存储的是native本地方法的栈帧。在Hotspot虚拟机中，Java虚拟机栈和本地方法栈实现上使用了同一个栈空间。
  • 本地方法栈会在栈内存上生成一个栈帧，临时保存方法的参数同时方便出现异常时也把本地方法的栈信息打印出来。

3.3堆内存

存储对象实例、数组、静态变量（1.7之前存在方法区）和字符串常量池（1.7之前存在方法区），是 JVM 最大的内存区域，也是 GC（垃圾回收）的主要目标。

3.3.1堆空间的结构

堆空间有三个需要注意的值，used、total和max

used指的是当前已使用的堆内存，total是java虚拟机已经分配的可用堆内存，max是java虚拟机可以分配的最大堆内存。如果used 接近 total 且 GC 后仍不足，也就是total接近满了那么可以根据规则向max进行扩展。

3.3.2堆空间大小的设置

如果不设置任何的虚拟机参数，max默认是系统内存的1/4，total默认是系统内存的1/64。在实际应用中一般都需要设置total和max的值。

  • 要修改堆的大小，可以使用虚拟机参数-Xmx(max最大值)和-Xms(初始的total)。
  • 语法：-Xmx值 -Xms值
  • 单位：字节(默认，必须是1024的倍数)、k或者K(KB)、m或者M(MB)、g或者G(GB)
  • 限制：Xmx必须大于 2MB，Xms必须大于1MB

建议将total和max设置成相同的值，这样就减少了申请并分配内存的时间消耗

3.3.3字符串常量池

字符串常量池中存放的是字符串的引用，当通过字面量创建字符串时，jvm会先检查常量池，若没有引用，则在堆中创建 String 对象，再将该对象的引用存入常量池

在早期设计中，字符串常量池是属于运行时常量池的一部分，存放在方法区（永久代）中。在jdk1.7之后的版本将字符串常量池分离出来，放到了堆中。

目的：

  1. 解决永久代内存瓶颈：永久代内存上限固定且偏小，字符串常量池动态性强，易触发 PermGen OOM；迁移到堆后可利用堆的大内存空间和灵活扩容机制，大幅降低溢出风险。
  2. 提升常量回收效率：永久代仅在 Full GC 时回收无用常量（STW 时间长、频率低）；堆支持 Minor GC 高频清理短生命周期常量，减少内存闲置，同时降低 Full GC 触发频率。
  3. 规避永久代设计缺陷：永久代存储类元数据 + 常量易产生内存碎片，且回收粒度粗；堆的分代 GC 与内存分配机制（如 TLAB）更适配字符串常量池的动态增删需求，提升内存利用率。

讲一下String.intern()方法，可以手动将字符串放到字符串常量池中，如果相同的字符串多次使用intern，那么他们的引用也是相同的

问题1：对象的引用是在哪里存放？

如果对象引用是局部变量（方法内声明），则会在栈帧的局部变量表中添加指向堆中对象的内存地址，比如Student s1 = new Student()，s1会存放在栈帧的局部变量表中指向堆中的实例，但是这种方法将地址存放到栈帧中实例是不能线程共享的。如果是静态变量 / 成员变量，则他们的引用在堆区，可以支持线程共享。

问题2：堆内存会不会溢出

堆内存会溢出，这是 JVM 运行中最常见的内存异常之一，对应的错误是java.lang.OutOfMemoryError: Java heap space(简称oom) ，以下是溢出的场景。

原因类型 具体场景
内存泄漏（最常见） 对象已无业务用途，但仍被引用（如静态集合持有大量对象引用、未关闭的连接 / 流），GC 无法回收，堆被逐步占满
大对象直接创建 一次性创建超大对象 / 数组（如 new byte[10241024500]，500MB 的数组），超出堆剩余空间
并发请求过载 高并发场景下，短时间创建大量对象（如接口每秒接收 10 万请求，每个请求创建大量临时对象），GC 回收速度赶不上对象创建速度
堆配置过小 堆的最大内存（-Xmx）配置远小于业务所需（比如给处理大数据的程序配 128M 堆）
内存泄漏 + 并发叠加 内存泄漏导致堆可用空间逐步减少，叠加并发请求后，最终触发溢出（生产环境最典型）

3.4方法区

方法区是线程共享的，主要存储类的元信息、运行时常量池和static final常量

  • 类的元信息：在加载阶段，类加载器将字节码信息读取到内存中，并且创建一个InstaceKlass对象用来存储元信息。

  • 运行时常量池：字节码文件中通过编号查表的方式找到常量，这种常量池称为静态常量池。当常量池加载到内存中之后（在连接的解析阶段），可以通过内存地址快速的定位到常量池中的内容，这种常量池称为运行时常量池。

3.4.1方法区结构

方法区是jvm规定的一个逻辑概念，在**HotSpot虚拟机中，*它的具体实现方式先后有*永久代 和 元空间两种。

JDK7及之前的版本将方法区存放在堆区域中的永久代空间，堆的大小由虚拟机参数来控制。

JDK8及之后的版本将方法区存放在元空间中，元空间位于操作系统维护的直接内存中，默认情况下只要不超过操作系统承受的上限，可以一直分配。

3.4.2方法区溢出

方法区存储的类元数据、常量等超出其内存限制，触发 OutOfMemoryError，不同实现（永久代 / 元空间）表现不同：

  1. 永久代（JDK7 及之前）：方法区通过永久代实现，有固定内存上限（-XX:MaxPermSize），若大量动态生成类（如动态代理、JSP 编译）、常量堆积，且类加载器无法回收，会抛出 OOM: PermGen space。
  2. 元空间（JDK8 及之后）：方法区改用元空间（本地内存），默认无上限，但显式设置 - XX:MaxMetaspaceSize 或本地内存耗尽时，会抛出 OOM: Metaspace，核心诱因仍是类元数据堆积（类加载器未回收）。

3.5直接内存

3.5.1核心特点

  1. **不属于 JVM 运行时数据区：**JVM 规范定义的内存区域（堆、虚拟机栈、方法区等）里没有直接内存，它是 HotSpot 等虚拟机为提升 I/O 性能而引入的**扩展内存区域**。
  2. 分配与释放由开发者 / 工具类控制：直接内存主要通过 java.nio.ByteBuffer 类的 allocateDirect(int capacity) 方法分配，底层调用操作系统的 malloc 等函数申请本地内存。
  3. 不受 Xmx 限制，但受物理内存限制：堆内存的上限由 Xmx 参数指定，而直接内存的大小默认不受此参数约束。但如果直接内存 + 堆内存总和超过物理内存，会触发操作系统的内存交换（Swap），导致程序性能急剧下降，甚至 OOM。

3.5.2核心作用

直接内存的设计目的是避免 JVM 堆和本地内存之间的数据拷贝，解决传统 I/O 的性能瓶颈，NIO 的设计目标是非阻塞 + 零拷贝。直接内存属于本地内存的用户态内存区域，不受JVM垃圾回收器管理。

  1. 传统 I/O 的数据拷贝流程：读取磁盘 / 网络数据时，数据会先从硬件拷贝到操作系统的内核缓冲区（本地内存），再从内核缓冲区拷贝到 JVM 堆内存，共 2 次拷贝，流程如下：硬件 → 内核缓冲区（本地内存） → JVM 堆内存（省略了硬件→dma的拷贝，拷贝物理地址，因为速度非常快，一般不记）
  2. 直接内存的零拷贝优化：**直接内存的零拷贝优化主要体现在**减少用户态与内核态之间的数据拷贝次数，不在内核页缓存 ↔ JVM 堆之间做内存复制**。JVM 调用 mmap 系统调用，将文件对应的物理页映射到用户态直接内存（用户态虚拟地址）。这样，用户态和内核态通过不同的虚拟地址访问同一组物理内存页。Java 程序通过 DirectByteBuffer 操作直接内存（用户态虚拟地址），**本质是读写其**映射的物理内存页，从而避免了将数据拷贝到 JVM 堆内存。这里说的零拷贝只是语义上的（只减少一次copy）。（简单理解就是通过系统调用将直接内存映射到物理内存，jvm通过访问直接内存来访问物理页**）

四、垃圾回收

Java中为了简化对象的释放，引入了自动的垃圾回收（Garbage Collection简称GC）机制。通过垃圾回收器来对不再使用的对象完成自动的回收，垃圾回收器主要负责对堆上的内存进行回收。其他很多现代语言比如C#、Python、Go都拥有自己的垃圾回收器。

4.1方法区的回收

方法区的内容主要是不再使用的类

判定一个类可以被卸载（类元数据卸载）。需要同时满足下面三个条件:

  1. 此类所有实例对象都已经被回收，在堆中不存在任何该类的实例对象以及子类对象。
  2. 加载该类的类加载器已经被回收。
  3. 该类对应的 java.lang.Class 对象没有在任何地方被引用。

如果需要手动触发回收，可以使用System.gc()方法。调用Svstem.gc()方法并不一定会立即回收垃圾，仅仅是向Java虚拟机发送一个垃圾回收的请求，具体是否需要执行垃圾回收JVM会自行判断。

问题：只有自定义类加载器才可能会被回收，其他几乎不会。开发中此类场景一般很少出现，主要在如JSP 的热部署等应用场景中，每个jsp文件对应一个唯一的自定义类加载器。当一个jsp文件修改了，就直接卸载这个jsp类加载器。重新创建类加载器重新加载jsp文件。

4.2堆回收

堆内存回收的条件：Java中的对象是否能被回收，是根据对象是否被引用来决定的。如果对象被引用了，说明该对象还在使用，不允许被回收。

A和B不能被回收

让a1=null，b1=null后，使用可达性分析法可以被回收

4.2.1引用计数法和可达性分析

  1. 引用计数法会为每个对象维护一个引用计数器，当对象被引用时加1，取消引用时减1。缺点：每次引用和取消引用都需要维护计数器，对系统性能会有一定的影响；存在循环引用问题，所谓循环引用就是当A引用B，B同时引用A时会出现对象无法回收的问题。
  2. 可达性分析法，java使用的是可达性分析算法来判断对象是否可以被回收。可达性分析将对象分为两类：垃圾回收的根对象(GC root)和普通对象，对象与对象之间存在引用关系。

jvm会持有一个所有gc root对象的列表，通过引用链可以找到的对象则不能被回收

哪些对象是cg rooy对象呢？

  • 线程Thread对象，引用线程栈帧中的方法参数、局部变量等

线程对象存放在堆内，每一个线程对象都会有一个对应的栈内存

  • 应用类加载器加载的java.lang.Class对象

每个被加载的类，在 JVM 里都会有一个 java.lang.Class 对象

  • 监视器对象，是 JVM 内部的数据结构，用来实现sychronzied

sychronzied关键字持有的对象不可被回收，可以找到监视器gc root

  • 本地方法调用时的全局 对象

4.3五种对象引用

可达性算法中描述的对象引用，一般指的是强引用，GCRoot对象和普通对象有引用关系，普通对象就不会被回收。除此之外java还有四种引用，总共五种

  • 强引用
  • 软引用
  • 弱引用
  • 虚引用
  • 终结器引用

4.3.1强引用

强引用（Strong Reference） 是最基础、最常用的引用类型，也是默认的引用方式 —— 只要一个对象被强引用关联，JVM 就会认为这个对象是 “必须存活的”，无论内存是否充足，都不会被 GC 回收，直到所有强引用被断开。

所有直接通过赋值、参数传递等方式创建的引用，默认都是强引用。只有主动断开所有强引用，对象才会失去 “存活标识”，进而可能被 GC 回收。

注意几个误区：

  1. 置为 null 后对象立即被回收

user = null 只是断开了强引用，但对象不会 “立即” 被回收 。GC 回收是异步的，只有当 GC 执行可达性分析，发现对象无任何 GC Root 引用（包括强 / 软 / 弱引用）时，才会标记为可回收，最终在 GC 阶段清理。

  1. 局部变量的强引用在方法结束后自动消失

方法内的局部变量（如 test() 中的 u）存储在虚拟机栈的栈帧中，方法执行完毕后栈帧销毁，对应的强引用会自动消失 —— 这是栈内存的特性，而非强引用本身的特殊逻辑。

4.2.2软引用

如果一个对象只有软引用关联到它，当内存不足时，触发GC，就会将软引用中的数据回收，如果还是不足就会抛出OutOfMemory异常，常用于缓存。

通过SoftReference类实现软引用

当软引用对象被回收后，软引用实例本身仍会存在，也就是说软引用本身也应该被回收。软引用指向的对象在内存不足时会被自动回收，那软引用本身要怎么去实现回收呢？

SoftReference提供了一套队列机制，软引用创建时，可以通过构造器传入引用队列。在软引用中包含的对象被回收时，该软引用本身会被放入引用队列。然后通过遍历队列把软引用对象（SoftReference 实例）进行删除。

4.2.3弱引用

弱引用（Weak Reference） 是比软引用更 “弱” 的引用类型。只要发生垃圾回收（GC），无论内存是否充足，被弱引用关联的对象都会被立即回收。弱引用主要使用在ThreadLocal中，弱引用对象本身也要通过引用队列回收。

4.2.4虚引用

虚引用（Phantom Reference） 是最弱的一种引用类型。无法通过虚引用获取目标对象，仅能作为 “对象即将被回收” 的通知手段—— 它的唯一作用当对象被垃圾回收器回收时可以接受到对应的通知，而非使用对象本身。

创建虚引用时必须关联 ReferenceQueue（引用队列），否则无法实例化（构造方法会抛异常）。虚引用无法通过 get() 方法获取目标对象（永远返回 null），仅能通过 ReferenceQueue 监听对象回收事件。

直接内存中，为了及时知道直接内存对象不再使用，从而回收内存，使用了虚引用来实现。

4.2.5终结器引用

终结器引用（Finalizer Reference） 是一种特殊的、由 JVM 内部管理的引用类型（属于虚引用的子类），专门用于关联重写了 finalize() 方法的对象，核心作用是触发对象的 finalize() 方法执行，并控制对象的最终回收时机。

4.5垃圾回收算法的评价标准

垃圾回收的过程简单来说就是两件事：

  1. 找到内存中存活的对象
  2. 释放需要回收的对象的内存，是的程序能够再次利用这部分空间

Java垃圾回收过程会通过单独的GC线程来完成，但是不管使用哪一种GC算法，都会有部分阶段需要停止所有的用户线程。这个过程被称之为Stop The World简称STW（只有gc线程运行），如果STW时间过长则会影响用户的使用。

评价标准：

  1. 吞吐量：吞吐量指的是 CPU 用于执行用户代码的时间与 CPU 总执行时间的比值，即吞吐量=执行用户代码时间/(执行用户代码时间 +GC时间)。吞吐量数值越高，垃圾回收的效率就越高。
  2. 最大暂停时间：指所有在垃圾回收过程中的STW时间的最大的一个暂停时间
  3. 堆使用效率：不同垃圾回收算法，对堆内存的使用方式是不同的。比如标记清除算法可以使用完整的堆内存。而复制标记清除算法要优于复制算法。复制法会将堆内存一分为二，每次只能使用一半内存。

一个垃圾回收算法无法同时让所有评价变好，不同的垃圾回收算法适用于不同的场景。

4.6垃圾回收算法（回收思想）

4.6.1标记清除算法

核心分为两个阶段：

  1. 标记阶段，将所有存活的对象进行标记。Java中使用可达性分析算法，从GCRoot开始通过引用链遍历出所有存活对象。
  2. 清除阶段，从内存中删除没有被标记也就是非存活对象。

优点：实现简单，

缺点：

  1. 碎片化问题。由于内存是连续的，所以在对象被删除之后，内存中会出现很多细小的可用内存单元。如果我们需要的是一个比较大的空间，很有可能这些内存单元的大小过小无法进行分配。
  2. 分配速度慢。由于内存碎片的存在，需要维护一个空闲链表，极有可能发生每次需要遍历到链表的最后才能获得合适的内存空间。

4.6.2复制算法

核心思想：

  1. 准备两块空间From和To空间，每次在对象分配阶段，只能使用From空间
  2. 在垃圾回收阶段，将From中存活对象（GCroot及其相连对象）复制到To空间，
  3. From剩下的就是需要回收的对象，清理From并将两块空间的名字进行互换

优点：

  1. 吞吐量高。复制算法只需要遍历一次存活对象复制到To空间即可，比标记-整理算法少了一次遍历的过程，因而性能较好，但是不如标记-清除算法因为标记清除算法不需要进行对象的移动
  2. 不会发生碎片化。复制算法在复制之后就会将对象按顺序放入To空间中，所以对象以外的区域都是可用空间，不存在碎片化内存空间。

缺点：

内存使用效率低。每次只能让一半的内存空间来为创建对象使用。

4.6.3标记整理算法

是对标记清除算法容易产生内存碎片的一种解决方案。

核心思想分为两个阶段：

  1. 标记阶段。将所有存活的对象进行标记。使用可达性分析算法，从GC Root开始通过引用链遍历出所有存活对象。
  2. 整理阶段。将存活对象移动到堆的一段，清理掉非存活对象的内存空间。

优点：

  1. 内存使用效率高，使用整个堆空间
  2. 不会发生内存碎片化

缺点：

整理阶段的效率不高

4.6.4分代GC

分代GC将整个内存区域划分为新生代和老年代，对不同代的对象特征，选择适配的GC算法和回收策略，最终实现低 STW 时长 + 高回收效率的平衡。

分代 存储对象特征 内存占比（默认） 核心回收算法 回收触发名称
新生代 新创建的对象、生命周期极短（90% 以上很快被回收） 约 1/3 堆内存 复制算法 Minor GC
老年代 存活过多次 Minor GC 的对象、大对象、长生命周期对象 约 2/3 堆内存 标记 - 整理 / 标记 - 清除 Major GC/Full GC
元空间 存储类元数据、常量池等（非堆，直接内存） 受本机内存限制 元空间 GC（独立） -

新生代内部又拆分为：

  • 伊甸区：新对象优先分配的区域；
  • 两个幸存者区（From/To）：大小相等，用于存放 Minor GC 后存活的对象，是复制算法的 “空闲区”。

分代 GC 的核心回收流程：

  1. 新生代回收（Minor GC）

这是分代 GC 中最频繁的回收（毫秒级 STW，用户几乎无感）：

  • 触发条件：伊甸区满，无法分配新对象；
  • 回收过程（复制算法）：① 暂停用户线程（STW），标记 伊甸区 + SurvivorFrom 区的存活对象；② 将存活对象复制到 SurvivorTo 区（对象 “年龄”+1，年龄记录对象经历的 Minor GC 次数）③ 清空伊甸区和SurvivorFrom区，互换 From/To 区的身份；④ 若 SurvivorTo 区空间不足，存活对象直接 “晋升” 到老年代；
  • 特点：存活对象少，复制成本低，STW 时长极短（通常几毫秒）。
  1. 老年代回收（Major GC/Full GC）

老年代回收频率低，但 STW 时长更长（百毫秒～秒级，需重点优化）：

  • 触发条件（核心）：① 老年代内存不足（如新生代对象晋升、大对象直接分配）② Minor GC 后晋升老年代的对象大小 > 老年代剩余空间；③ 显式调用System.gc()（不推荐，JVM 可忽略）④ 元空间不足触发的 Full GC（连带回收老年代）

  • 回收过程

    （标记 - 整理 / 标记 - 清除）：① 暂停用户线程（STW），标记老年代的存活对象；② 整理阶段：将存活对象压缩到内存一端，消除碎片（或直接清除垃圾，如 CMS）；③ 清空垃圾区域，重置内存分配指针；

    • 特殊情况（Full GC）：若触发 Full GC，会同时回收新生代 + 老年代，STW 时长更长。
  1. 分代 GC 的 “代际联动”

新生代和老年代并非完全独立，核心联动逻辑：

  • 新生代 Minor GC 的 “晋升机制” 是老年代对象的主要来源；
  • 老年代内存不足时，会触发更耗时的 Major/Full GC，甚至可能 “提前触发 Minor GC” 以释放新生代空间，减少晋升压力；
  • 部分 GC（如 G1）会打破严格的分代边界，以 “Region” 为单位混合回收新生代和老年代，但仍保留分代的核心思想。

新生代用高效的复制算法频繁轻量回收，老年代用标记 - 整理 / 清除算法低频重度回收

4.7垃圾回收器（实现垃圾回收算法的具体手段）

4.7.1G1垃圾回收器

G1 GC是JDK9 + 默认垃圾回收器

G1 把堆拆成多个大小相等的 Region：

  • 物理上无分代：堆不再有 “新生代块”“老年代块”，而是一堆独立的、大小相同的 Region；
  • 逻辑上仍分代：每个 Region 可被动态标记为Eden/Survivor（新生代）或Old（老年代），甚至 Humongous（大对象区）；
  • 分代边界动态调整：新生代不再是固定的 1/3 堆，而是由若干 Region 组成，其占比可在运行中动态变化（比如业务高峰期新生代占比从 30% 涨到 50%）。

新生代、老年代和对象晋升逻辑不变

G1 的核心目标：

可控的 STW：通过XX:MaxGCPauseMillis（默认 200ms）设置目标暂停时间，G1 会智能选择回收的 Region 组合，确保 STW 不超阈值；

垃圾优先回收：优先回收垃圾占比高的 Region（“Garbage-First” 的由来），用最少的 STW 时间释放最多的内存；

无内存碎片：回收时通过复制算法整理 Region，天然消除碎片；

适配大堆：堆内存从 4GB 到 64GB 都能高效管理（超过 64GB 建议选 ZGC）。

G1 的核心回收流程：

1. 新生代回收（Young GC）—— 高频、短 STW

这是 G1 最频繁的回收，逻辑类似传统新生代的复制算法，但以 Region 为单位：

  • 触发条件：Eden Region 不足以为新对象分配内存；
  • 回收过程（STW，毫秒级）：
    1. 暂停所有用户线程，标记所有 Eden + Survivor Region 中的存活对象；
    2. 将存活对象复制到空的 Survivor Region（年龄 + 1）或 Old Region（Survivor 空间不足时）；
    3. 清空原 Eden/Survivor Region，标记为 “空闲”；
  • 特点：仅回收新生代 Region，存活对象少，STW 通常在 10~50ms，用户几乎无感。

2. 并发标记 —— 无 STW，为混合回收做准备

当堆内存使用率达到阈值（默认 45%，-XX:InitiatingHeapOccupancyPercent），触发并发标记，目的是统计所有 Old Region 的垃圾占比：

  1. 初始标记（STW，极短）：标记 GC Roots 直接引用的存活对象（仅几毫秒）；
  2. 并发标记（无 STW）：和用户线程并行，遍历所有 Region 的引用链，标记存活对象；
  3. 最终标记（STW，短）：修正并发标记期间用户线程修改的引用（使用 SATB 快照算法，避免漏标）；
  4. 清理统计（无 STW）：计算每个 Old Region 的 “垃圾占比”，排序生成 “回收优先级列表”。

3. 混合回收（Mixed GC）—— 核心，平衡延迟与效率

这是 G1 回收老年代的核心方式，也是 “垃圾优先” 的体现：

  • 触发条件：并发标记完成后，Old Region 的垃圾占比达到阈值；
  • 回收过程（STW，可控）：
    1. 暂停用户线程，从 “优先级列表” 中选择一批垃圾占比最高的 Old Region + 所有新生代 Region；
    2. 将这些 Region 中的存活对象复制到空闲 Region（压缩整理，无碎片）；
    3. 清空原 Region，标记为空闲；
  • 特点：
    • 每次只回收部分 Old Region（而非整堆），确保 STW 不超过MaxGCPauseMillis；
    • 混合回收会执行多次，直到 Old Region 的垃圾占比降至阈值以下。

4. Full GC —— 极端情况，需避免

G1 的 Full GC 是 “兜底方案”，仅在内存分配极端不足时触发：

  • 触发条件：混合回收无法及时释放内存（如大对象分配失败、并发标记超时）；
  • 回收过程：退化为传统的 “整堆标记 - 整理”，全程 STW，时长可达数百毫秒～秒级；
  • 优化目标：通过合理调优，让 Full GC “几乎不发生”。
