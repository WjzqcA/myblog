# 一、索引优化

没有索引的字段查找使用全表扫描，如果有索引那就使用对应的B+树

## 1.1 I/O的理解

数据库运行的性能瓶颈往往是**磁盘访问（I/O）**，因为：

- 磁盘速度远低于内存和CPU
- InnoDB 的一次 I/O 操作**至少读取或写入一个 16KB 的页**（MySQL InnoDB 默认页（逻辑页）大小是 **16KB**）
- 每一次访问节点（如树结构中的某个节点），如果它不在内存中，都会触发一次**磁盘I/O**

因此，数据库的数据结构必须尽量**减少磁盘I/O次数**。

## 1.2 索引的数据结构

### 2.2.1 哈希表的缺点

- **不支持范围查询**：哈希打乱顺序，无法处理 `>`, `<`, `BETWEEN`, `LIKE 'abc%'` 等。
- **不支持排序**：`ORDER BY` 无法利用哈希索引，加重排序负担。
- **不支持前缀或模糊匹配**：哈希基于整体值，无法匹配部分字段。
- **哈希冲突影响性能**：冲突多时查找效率下降。
- **不支持联合索引最左匹配**：组合哈希无法单独使用前缀字段。
- **维护成本高**：频繁插入或删除易导致 rehash，性能抖动。
- **不支持覆盖索引（InnoDB）**：无法直接从索引中获取数据，需回表。

### 2.2.2 二叉树的缺点

向二叉树中插入数据会让树的高度不断变高。

普通树的数据结构是为**内存使用设计的**，不是为磁盘设计的，如果把这些结构存储到磁盘，**每个节点都可能分布在不同的页上。所以读取一条路径需要 N 次 I/O，效率非常低 （一个节点只包含 1 个 key + 2 个指针）**。

### 2.2.3 B树的缺点

![B+树结构](/image/数据库优化/img1.png)

数据库（如 InnoDB）在设计 B/B+树时，**会将一个“节点”设计成刚好填满一个磁盘页的大小**

在 B树 中：中间节点 = key + 数据 ⇒ 每页容纳的数据项更少，同样的数据量B树更高，查询路径越长（根据sql中的id查跟，在一步一步查下去）

### 2.2.4 B+树

![B树和B+树对比](/image/数据库优化/img2.png)

## ✅ 为什么数据库不用 B树，而选择 B+树？

### 📌 1. B+树中间节点不存数据 ⇒ 更高的扇出 ⇒ 更低的树高 ⇒ 更少 I/O

- 在 B树 中：中间节点 = key + 数据 ⇒ 每页可容纳更少项
- 在 B+树 中：中间节点只存 key ⇒ 每页容纳更多项 ⇒ **更高扇出**

✅ 更高扇出意味着：

- 同样数据量，B+树的高度更低
- ⇒ 查找路径更短
- ⇒ **I/O 次数更少**

---

### 📌 2. B+树天然支持范围查询、区间查找、更高效排序（hash索引不行）

- 由于 B+树 **所有数据都在叶子节点**，而叶子节点是**链表连接、有序排列**的
- 所以只需要一次查找到区间起点，然后**顺着链表往后走**就能获取范围内所有数据

✅ 优点：

- **范围查询效率极高**

- 适用于 SQL 中的：

  ```sql
  WHERE age BETWEEN 30 AND 50;
  ORDER BY age;
  ```

❌ 而 B树 中数据分布在所有节点，遍历范围就必须做 **全树遍历（更慢）**

---

### 📌 3. B+树查询一致性更好（必须查到叶子节点）

在 B+树 中：

- 所有查询都必须查到叶子节点才能得到数据
- 所以所有查询路径长度一致，容易预测和优化缓存

❌ B树 查询可能在中间节点结束（路径不一致），不利于批处理、缓存命中预测

---

### 📌 4. B+树便于批量顺序读写、IO合并（磁盘优化）

- 由于叶子节点是有序链表 ⇒ B+树可以**顺序访问磁盘页**
- 顺序 I/O 性能远高于随机 I/O
- 操作系统也可以做 **预读优化**，提前读多个连续页到缓存中

✅ 更适合磁盘、SSD 的 I/O 模型

## 1.3索引的类别

![](/image/数据库优化/img3.png)

在InnoDB存储引擎中，根据索引的存储形式，也可以分为以下两种

![](/image/数据库优化/img4.png)

**聚集索引：**包含所有的字段，索引的 key是表中的某个字段，B+树根据这个字段进行构建（innoDB下数据库中数据的存储其实就是以聚簇索引的结构存储在磁盘上）

**二级索引：**是索引字段的数据以及对应数据的主键

聚集索引的选取规则：

- 如果存在主键，主建索引为聚集索引
- 如果不存在主键，使用第一个唯一索引作为聚集索引
- 如果都没有，InnoDB会自动生成一个rowid作为隐藏的聚集索引

**二级索引如何查找数据：**

首先通过二级索引的B+树找到id，然后在到聚簇索引中根据id找到对应数据（也叫做**回表**）

## 1.4索引的创建语句

- 创建索引：CREATE INDEX index_name ON table_name(column1, column2);

一个索引可以关联多个字段（联合索引）

- 查看索引：SHOW INDEX FROM table_name;
- 删除索引：DROP INDEX index_name ON table_name;

## 1.5索引使用规则

### 最左前缀法则

在联合索引中，查找时只有**左边的那个字段存在**，右边的才能够被使用到（联合索引才有效）

如果跳过了中间的某一个字段，索引部分失效（被跳过的到最后的字段都失效）

🔍原因：因为联合索引的B+树是按照从左到右排序的（查找时先对比前面的字段，如果相等再对比后面的字段），只有提供前一个索引的信息才能对后面的查找后面的索引列

### 范围查询

联合索引中，出现范围查询（如 <, >、<=、>=、BETWEEN），范围查询右侧的索引失效

🔍原因：范围查询会有多个索引A的值，那么下一个**索引B的查询会跨域多个A**，那么B的值就会变得无序，无法利用b+树继续判断查找

### 索引失效

- **运算操作**：索引进行运算操作的话索引会失效
- **字符串不加引号**，索引将失效
- 尾部模糊匹配不会失效，**头部模糊匹配会失效**
- 用or连接，如果or**前的列有索引，后面的列没有索引**，那么涉及到的索引都不会被用到（两侧都有索引才会生效）
- 如果mysql评估使用索引比全表更慢，则不使用索引

### SQL提示

如果一个字段涉及到多个索引，默认mysql会自己选择。sql提示是人为选择来达到优化操作的目的，有三个挡位：建议使用，不用，必须用。

![](/image/数据库优化/img5.png)

### 覆盖索引

select **id,name,age** from table where name ='zhangsan'

⚠️如果建立name的单列索引，会因为没有age信息而回表

所以要建立（**name,age** ）的联合索引可以避免这个查询出现回表

🔍当查询条件为联合索引的全部或者其中的一个字段都会使用这个联合索引

**这种索引的叶子节点包含了查询的所有字段就叫做索引覆盖**

### 前缀索引

当索引是很长的字符序列时，这个索引将会很占硬盘，而且会很慢，这时候就会用到前缀索引了。所谓的前缀索引就是将索引的前面几个字母作为索引，但是要降低索引的重复率，**我们还必须要判断前缀索引的重复率**。

索引选择性：指的是不重复的索引值（基数）和表记录数的比值。选择性是索引筛选能力的一个指标。取值范围是 0—1**(不用前缀为1) **，当选择性越大，索引价值也就越大。

索引选择性 = 基数 / 总行数

```
SELECT COUNT(DISTINCT(school_name))/COUNT(id) AS Selectivity FROM school;
```

# 三、字段类型设计

## 3.1 Mysql包含的数据类型

| 类型分类   | 常见类型                            |
| ---------- | ----------------------------------- |
| 数值型     | INT, BIGINT, DECIMAL, FLOAT, DOUBLE |
| 日期时间型 | DATE, DATETIME, TIMESTAMP           |
| 字符串型   | CHAR, VARCHAR, TEXT, ENUM, BLOB     |

## 3.2 如何选择数据类型

### 数值类型

**尽量精确选择整型大小**

> 根据实际范围选择 TINYINT（一个字节） / SMALLINT（两个）/ INT（四个） / BIGINT（八个），
>  不要一律用 INT，浪费空间、影响缓存效率。

 **UNSIGNED表示无符号，会改变数据范围**

> UNSIGNED INT范围为 0 ~ 42亿，比有符号型翻倍。

 **金额用 DECIMAL，不要用 FLOAT 或 DOUBLE**

> 浮点型存在精度误差，不适合存储货币等，DECIMAL是精确小数（按字符串模拟十进制，效率存储性能较差），适合金融计算

### 字符串类型

**优先使用 VARCHAR，少用 TEXT**

> TEXT是专用于大文本内容的类型，存储方式更复杂。TEXT 超出一定长度会存在独立表中，不能建普通索引，效率低。

**VARCHAR 最大长度受行大小限制（65,535字节）**

> 多列合起来也不能超过这个限制，尤其使用 UTF8MB4 时注意（一个字符最多占 4 字节）。

**不要用 `CHAR` 存变长数据**

> CHAR(n) 会强制补足空格，浪费存储空间。

**短固定字段（如状态、性别）用 CHAR(1) 更高效**

> 定长更适合长度固定且小的数据，减少碎片。

### 日期类型

**推荐使用DATETIME表示时间点**

> 它不受时区影响，适合跨地区场景。

 **TIMESTAMP受时区影响，存储的是 UTC，自动转换**

> 插入时会转换为 UTC，查询时根据时区转换回本地时间。

**不要用YEAR存储生日或年份信息**

> 可读性差、范围小（只支持 1901–2155）。

**使用时间范围时注意格式匹配**

> 比如BETWEEN '2025-01-01' AND '2025-01-31'，格式不一致可能匹配不到。
